# v1.5.0 Release Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v1.5.0 as a single minor release covering both Track A (Java/Ruby/.NET SDK parity + P0 fixes + naming standardization) and Track B (Dependency Visualization backend + dashboard). This is the final phase (Phase 7) of the v1.5.0 upgrade, executing after all prerequisite phases (1-6) have merged to `develop`.

**Architecture:** This phase performs zero code changes. It orchestrates version bumps, CHANGELOG consolidation, develop→main promotion, git tagging, GitHub release creation, and verification that CI/publish pipelines succeed. The version number for the release is `v1.5.0` — a single minor increment per SemVer (additive capabilities + bug fixes, no breaking changes). Track A's three SDK packages each independently bump their own versions according to their ecosystem's SemVer conventions; Track B adds new REST endpoints but changes no existing APIs, so no SDK version bumps are required for the TS/Python SDKs.

**Tech Stack:** git, GitHub CLI (`gh`), bash, semantic versioning. No build tooling is invoked directly by this plan — CI pipelines handle all build/publish automation upon detecting the `v1.5.0` tag.

## Global Constraints

- Version bumps are MINOR only per SemVer (additive capability + bug fixes, no breaking changes).
- SDK version bump reasoning: Java (0.1.1 → 0.2.0 — new capability: full 5-step eval pipeline + hashVersion=2); Ruby (0.1.0 → 0.2.0 — same new capability + P0 entrypoint fix); .NET (0.1.0 → 0.2.0 — same new capability + P0 test-project fix). All three gain steps 2-4 (prerequisites, target-list, rule matching) + FNV-1a v2 hash, which is a substantial additive feature set justifying a minor bump.
- TS and Python SDKs: NO version bumps — neither Track A nor Track B modifies their code. `@flagmind/core` stays at `0.1.0`; `tombstone-sdk` (Python) stays at `0.2.1`.
- Root workspace `package.json` version: NO bump — stays at `0.1.0`. This is a monorepo coordination field only, not a published package.
- Dependency Visualization adds two REST endpoints (`GET /api/v1/graph/dependencies`, `GET /api/v1/graph/critical-flags`) and one MCP tool (`tombstone_get_dependency_graph`) — purely additive, no breaking changes to existing APIs.
- Branch: this plan does NOT cut its own branch — it runs on `develop` after all prerequisite PRs have merged.
- PR workflow: this plan opens a single `develop` → `main` promotion PR. The user merges it; the plan then creates the git tag and GitHub release.
- Verification commands are real git/gh commands with real expected-output descriptions — no fabricated state.

## Assumptions & State Dependencies

This plan makes the following assumptions about state that will not be known until Phases 1-6 actually land on `develop`:

1. **SDK version numbers at plan-execution time:** The version bump choices (Java 0.1.1 → 0.2.0, Ruby/NET 0.1.0 → 0.2.0) assume the current versions on `develop` are `0.1.1` (Java) and `0.1.0` (Ruby/.NET) at the time Task 3 runs. If Phases 2-4's implementers bump versions during their own phases (unlikely but possible), this plan's sed commands in Task 3 will fail to match and need adjustment. Mitigation: Task 3's verification steps (Steps 2, 4, 6) will catch mismatches immediately and report the actual current version, allowing the implementer to adjust the sed pattern on the fly.

2. **PR numbers:** The CHANGELOG entry in Task 2 cites PR numbers for Phases 1-6. These numbers are not known at plan-writing time. The plan instructs the implementer to fetch them via `gh pr list` (Task 2 Step 1) and insert them into the CHANGELOG draft. If `gh` is unavailable, the plan falls back to citing commit SHAs instead of PR numbers — this is acceptable per CHANGELOG.md's existing convention (some entries cite PR numbers, some cite commit SHAs or file paths without a PR reference).

3. **Helm chart version:** The Helm chart's `version:` field in `infra/helm/tombstone-operator/Chart.yaml` is independent of the Tombstone platform version. This plan does not bump the chart version — it assumes the chart version is set appropriately by the operator maintainer outside of this release cycle. Task 6 Step 4 reads the current chart version from the file rather than hardcoding `0.2.0`, so the plan adapts to whatever chart version exists at runtime.

4. **User merges the PR:** Task 4 opens a `develop` → `main` PR but does NOT merge it automatically. The plan pauses and explicitly instructs the user to merge the PR manually (per this repo's established workflow in BRANCHES.md). Task 5 resumes only after the user confirms the merge. This is a design choice (not an assumption) — the assistant proposes PRs but the user controls main-branch commits.

5. **CI workflow existence:** The plan assumes `.github/workflows/docker-publish.yml` and `.github/workflows/helm-publish.yml` exist and are configured to trigger on tag pushes matching the pattern `v*`. These workflows are present in the repo today (verified by reading the files earlier in this conversation). If they are modified or removed between now and plan execution, Task 6's verification steps will fail and report that no workflow runs were found, prompting investigation.
