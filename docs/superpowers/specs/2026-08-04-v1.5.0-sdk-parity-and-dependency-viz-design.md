# Tombstone v1.5.0 — SDK Parity + Dependency Visualization — Design

## 1. Scope & Goals

This upgrade has two independent tracks landing together in one release, v1.5.0.

**Track A — SDK Evaluation Parity.** Bring Java, Ruby, and .NET SDKs from "steps 1+5
only" up to the full 5-step evaluation pipeline (prerequisites, target-list match,
priority-sorted rule matching with full operator surface, both hash versions), fix two
newly-found P0 bugs (Ruby's broken `require "flagmind"` entrypoint, .NET's non-building
test project), and standardize naming across all three. TS and Python are **not
modified** — they keep their current shipped behavior; their mutual divergence is
documented as a known pre-existing issue, not fixed here.

**Track B — Dependency Visualization.** Expose the existing causal dependency graph
(`services/intelligence/app/graph/builder.py`) via new REST endpoints, and build a
dashboard UI: interactive force-directed graph, "what-if" disable-simulation, and a
critical-path / dependency-health ranking.

**Release goal**: close the single biggest documented correctness gap in the product
(SDK parity) without touching already-shipped TS/Python behavior, ship the
highest-leverage net-new capability that requires zero new external integrations, and
leave the codebase with an actual executable cross-language contract instead of the
doc-only parity matrix that exists today (`docs/SDK_CONTRACT.md`).

**Explicitly out of scope**:
- GitOps/OKE live-bootstrap validation — stays backlogged, blocked externally on Oracle
  Cloud signup (see `feedback-tombstone-gitops-verification` / `tombstone-v141-gitops-state`
  memory).
- Fixing the TS/Python mutual divergence itself.
- Session Replay Correlation, Cost & Performance Attribution (deferred net-new candidates).
- Any dependency/toolchain version bumps (e.g. `go.work` declares `go 1.22.0` while every
  service's `go.mod` says `go 1.25.0`) unless something in this design is blocked by them.
- Changes to the legacy Redis pub/sub path or the deprecated `gitops-sync` service.
- Regex targeting-rule operator — stays declared-but-unimplemented (matches current TS
  behavior of silently returning `false`), not a new bug introduced by this release.

## 2. Ground Truth (verified by direct source reading, not docs)

### 2a. Reference pipeline divergence — TS vs Python

Both `packages/sdks/@flagmind/core/src/evaluation.ts` (reference, TypeScript) and
`packages/sdks/flagmind-python/tombstone/evaluation.py` (reference, Python) implement the
full 5-step pipeline, but diverge from EACH OTHER:

| Aspect | TS | Python |
|---|---|---|
| OFF-path default | Parses `flagState.safeDefault` | Raw caller `default_value` |
| Prerequisite comparison | `String(value) !== requiredVariation` (multivariate-capable) | `bool(value) != required_value` (boolean-only, default `True`) |
| Prerequisite cycle handling | `MAX_PREREQ_DEPTH = 5` ceiling — fails open past that depth (skips ALL checks) | Explicit `seen_keys` chain — skips only the cyclic edge |
| Prerequisite memoization | None — full re-evaluation every time | Per-call `evaluation_cache` dict |
| Rule structure | Single attribute/operator/values triple per rule, no per-rule rollout | List of AND'd `conditions` per rule + its own `rollout_pct` sub-bucketing |
| Attribute resolution | Dot-notation nested paths on context, `attrs` fallback for single-segment names | Flat `attrs` dict only (plus special-cased `user_id`/`org_id`) |
| GEO operators | Implemented (`context.geo.country`/`region`, case-insensitive) | Not implemented, no `geo` field |
| Semver / date operators | Declared in `RuleOperator` but NOT implemented — silently returns `false` | Implemented (5 semver ops via `_padded_version`, 2 date ops) |
| String op case sensitivity | Case-**sensitive** (`contains`/`startsWith`/`endsWith`) | Case-**insensitive** (`.upper()` both sides) — real, live behavioral divergence between two shipped SDKs |
| Missing-attribute signaling | Silent `false`, no exception | `InconclusiveMatchError`, caught per-rule by the matching loop, `continue`s to next rule |
| Hash v1 (MurmurHash3) | `murmurhash.v3(flagKey+userId) >>> 0 % 100`, implicit library seed | `mmh3.hash(flag_key+user_id, seed=0, signed=False) % 100`, explicit seed — same net effect |
| Hash v2 (FNV-1a) | UTF-16 code-unit iteration | UTF-8 byte iteration — identical for ASCII, diverges for non-ASCII flag keys/user IDs |

Both agree on hash v1/v2 formula constants (offset `2166136261`, prime `16777619`, 10000-bucket
modulus for v2) and on `gate` intent (hard block vs soft skip), just not on comparison mechanics.

`test-contract/vectors.json` (v1.1, 24 vectors) covers ONLY hash algorithms. Zero vectors
exist for prerequisites, target-list, or rule-operator correctness in any language today —
this is the gap that let the case-sensitivity divergence above go unnoticed.

### 2b. Java/Ruby/.NET current state — confirmed via source + execution

All three SDKs implement **only steps 1 and 5** of the pipeline (preliminary check +
fallthrough rollout via MurmurHash3 v1). `EvaluationReason` enum members `TARGET_MATCH`,
`RULE_MATCH`, `PREREQUISITE_FAILED` are declared in all three but never constructed —
confirmed dead code. `FlagEnvironmentState` has exactly 7 fields in all three (`flagId`,
`flagKey`/`flag_key`, `environment`, `enabled`, `rolloutPct`/`rollout_pct`, `safeDefault`,
`updatedAt`) — missing `prerequisites`, `targetingRules`/`rules`, `targetList`, `hashVersion`
in all three. No `hash_version` field exists anywhere in any of the three, so FNV-1a v2 is
structurally unreachable, not merely unimplemented.

**New P0 bugs found (not in `docs/SDK_CONTRACT.md`):**

- **Ruby**: `lib/flagmind.rb` does `require_relative "tombstone/types"` (and 3 more) but no
  `lib/tombstone/` directory exists anywhere in the gem. `require "flagmind"` — the name
  matching the gem/package itself — throws `LoadError` immediately, confirmed by direct
  execution. The gem only works via the secondary alias `lib/tombstone.rb`, which itself
  contains `Tombstone = Flagmind unless defined?(Tombstone)` — a reference to a `Flagmind`
  constant that is defined nowhere in the codebase; this line only avoids erroring because
  `Tombstone` is already defined by the time it runs, short-circuiting the `unless`.
- **.NET**: `tests/FlagMind.Tests/FlagMind.Tests.csproj` has `<ProjectReference Include="..\..\src\Tombstone\Tombstone.csproj" />`, but only `src/FlagMind/FlagMind.csproj` exists on disk. The entire .NET test suite cannot build as currently checked in — root cause looks like a stale reference from a `Tombstone.csproj` → `FlagMind.csproj` rename where the test project's reference wasn't updated.

**Naming inconsistencies confirmed (differ in shape per SDK):**

- **Java**: Gradle `group = "io.tombstone"` (correct, matches product) vs Maven `artifactId = 'flagmind-java'` (stale).
- **Ruby**: gem name `flagmind-ruby`, working module `Tombstone` (not `Flagmind`), plus the broken vestigial `Flagmind` reference above.
- **.NET**: directory `flagmind-dotnet`, project/solution `FlagMind`/`FlagMind.csproj`, C# namespace/classes `Tombstone`/`TombstoneClient`, NuGet `PackageId` `Tombstone.Client` — four different names in simultaneous use.

## 3. Canonical Evaluation Spec (Track A)

For each TS/Python divergence, the target model for Java/Ruby/.NET resolves as follows.
TS and Python themselves are unchanged by this release — this table defines NEW code only.

| Divergence point | Canonical choice for Java/Ruby/.NET | Rationale |
|---|---|---|
| OFF-path default | Parse `flagState.safeDefault` (TS's approach) | Respects the flag's configured off-value instead of always falling back to the caller's default |
| Prerequisite comparison | String variation match against `requiredVariation` (TS's approach) | Supports multivariate prerequisite flags; boolean flags are just variation strings `"true"`/`"false"`, so no capability is lost |
| Prerequisite cycle handling | Explicit `seen` chain (Python's approach), not a depth ceiling | Detects the exact cycle edge instead of failing open past an arbitrary depth |
| Prerequisite memoization | Per-call cache dict (Python's approach) | Real perf requirement at "5,000+ flags" scale — the product's own stated thesis |
| Rule structure | Python's model: list of AND'd conditions per rule + per-rule `rollout_pct` sub-bucketing | Strictly more expressive; TS's single-condition model is a subset |
| Attribute resolution | Dot-notation nested paths with flat-attrs fallback (TS's approach) | More flexible for real-world nested user context (e.g. `geo.country`) |
| GEO operators | Included (TS's feature) | Common real-world targeting need; cheap given dot-notation resolution already supports it |
| Semver / date operators | Included (Python's feature, including the exact `_padded_version` padding algorithm, ported byte-for-byte) | Needed for version-gated rollouts; must match exactly to avoid a second silent divergence |
| Regex operator | Declared in the enum, NOT implemented (returns `false`, matches current TS behavior) | Neither reference SDK implements it — out of scope to invent new behavior here |
| String op case-sensitivity | Case-**insensitive** (Python's approach) | Python's behavior is already shipped and public (`tombstone-sdk` on PyPI); matching it avoids inventing a third "correct" answer. TS's case-sensitivity remains a known, unfixed pre-existing gap. |
| Missing-attribute signaling | Exception-based (language-idiomatic equivalent of Python's `InconclusiveMatchError`), caught by the rule-matching loop, `continue` to next rule | Explicitly distinguishes "could not evaluate" from "evaluated to false" |
| Hash v1 (MurmurHash3) | Confirm each SDK's existing implementation is correct — seed=0, unsigned 32-bit, mod 100, `concat(flag_key, user_id)` UTF-8 bytes | Already correct in all three per the audit; no change needed beyond adding the `hash_version` field to select it explicitly |
| Hash v2 (FNV-1a) | Port exactly, using UTF-8 byte iteration (Python's approach) | More portable across Java/Ruby/.NET's native string encodings than TS's UTF-16 code-unit iteration; both are equivalent for ASCII |

This table is the normative content that replaces the observational matrix in
`docs/SDK_CONTRACT.md`.

## 4. Contract Vectors Expansion

`test-contract/vectors.json` currently has 24 vectors, hash-algorithms only. This release
expands it to cover every dimension of the canonical spec, so "parity" has an objective,
automatable definition:

| Category | What it tests | Approx. count |
|---|---|---|
| `prerequisites` | Hard gate (met/unmet), soft gate (met/unmet), string-comparison mechanism (forward-compatible with future multivariate prerequisites, exercised here on boolean outcomes since no `variation`/value field is added to `FlagEnvironmentState` in this release), cycle detection, missing dependency, memoization sanity (same dep referenced twice) | ~10 |
| `target_list` | Match, no-match, empty list, empty user_id | ~4 |
| `rules_equality` | eq/neq/in/nin, single and multi-value | ~6 |
| `rules_string` | contains/startswith/endswith, case-insensitive assertion (mixed-case input, both sides) | ~6 |
| `rules_numeric` | gt/gte/lt/lte, boundary values, non-numeric input → inconclusive | ~6 |
| `rules_semver` | All 5 semver ops, prerelease ordering (`1.0.0-beta` vs `1.0.0`), build-metadata stripping, non-3-part versions | ~8 |
| `rules_date` | before/after, ISO-8601 with/without `Z`, malformed date → inconclusive | ~4 |
| `rules_geo` | country/region match, case-insensitive | ~4 |
| `rules_multi_condition` | Multiple AND'd conditions on one rule, per-rule rollout sub-bucketing (matched conditions but bucket outside rule's own `rollout_pct` → falls to next rule) | ~4 |
| `rules_priority` | Multiple rules, priority ordering, first-match-wins | ~3 |
| `missing_attribute` | Attribute absent from context → inconclusive, not false; rule skipped, evaluation continues | ~3 |

Each vector gets a flag-state/rule/prerequisite fixture, an input context, and an expected
result (value + reason). Java/Ruby/.NET each get a small vector-loading test harness (read
the JSON, run each case through their engine, assert output) — this becomes the executable
definition of "done" for each SDK, and the artifact that prevents a repeat of the TS/Python
silent-divergence failure mode for any future change in any language.

## 5. Per-SDK Work Plan (Track A)

Implementation order: Java → Ruby → .NET (sequential, so lessons from each carry forward).

### Java (`packages/sdks/flagmind-java/`)
- Add missing fields to `FlagEnvironmentState`: `prerequisites`, `targetingRules` (nested
  `conditions` + `rolloutPct`), `targetList`, `hashVersion`.
- Implement steps 2–4 in `EvaluationEngine`: prerequisite chain (`seen` set + memoization
  map), target-list check, priority-sorted rule matching with full operator surface
  (equality/string/numeric/semver/date/geo) + dot-notation attribute resolution.
- Add FNV-1a v2 hash alongside existing MurmurHash3 v1.
- Add an unchecked `InconclusiveMatchException`, thrown from operator evaluation, caught in
  the rule-matching loop.
- Fix dead `EvaluationReason` members — `TARGET_MATCH`/`RULE_MATCH`/`PREREQUISITE_FAILED`
  become reachable.
- Remove the dead unused `List<Object> rules` parameter on `evaluate(...)` or wire it in as
  intended (superseded by the new `targetingRules` field on `FlagEnvironmentState` — likely
  removable).
- **Naming cleanup**: standardize Maven `artifactId` to align with the `io.tombstone`
  package namespace (already correct) — e.g. `tombstone-java-sdk`.
- New vector-harness JUnit test class reading `test-contract/vectors.json`.

### Ruby (`packages/sdks/flagmind-ruby/`)
- **P0 fix first**: remove the broken `lib/flagmind.rb` (wrong `require_relative` paths +
  reference to nonexistent `Flagmind` constant); make a corrected single entrypoint file the
  canonical `require` target, working under the `Tombstone` module (already the functioning
  one).
- Same field/step/hash/exception additions as Java, idiomatic Ruby (`Struct` fields,
  `raise Tombstone::InconclusiveMatchError`, `rescue` in the rule loop).
- **Naming cleanup**: standardize gem name, module name, and file layout consistently on
  `Tombstone` — remove the vestigial `Flagmind` reference entirely.
- Vector-harness RSpec file.

### .NET (`packages/sdks/flagmind-dotnet/`)
- **P0 fix first**: fix `tests/FlagMind.Tests/FlagMind.Tests.csproj`'s `ProjectReference` to
  point at the real `src/FlagMind/FlagMind.csproj`.
- Same field/step/hash/exception additions, idiomatic C# (records, custom
  `InconclusiveMatchException`, `try/catch` in the rule loop).
- **Naming cleanup**: standardize project name, namespace, and NuGet `PackageId` on
  `Tombstone`/`Tombstone.Client` consistently; directory rename (`flagmind-dotnet` →
  something `tombstone`-aligned) deferred to a follow-up if git history preservation makes
  it awkward within this release — document the decision either way.
- Vector-harness xUnit `[Theory]` reading the JSON.

### Cross-cutting
- `docs/SDK_CONTRACT.md` rewritten from an observational matrix into the normative spec
  (Section 3 of this doc) plus an updated parity matrix showing all 5 SDKs at full 5-step
  parity, with TS/Python's mutual divergence called out explicitly as a documented,
  intentionally-unfixed pre-existing gap.

## 6. Dependency Visualization (Track B)

Independent of Track A — different services, different files, proceeds in parallel.

### Backend (`services/intelligence/`)
- New endpoint `GET /api/v1/graph/dependencies?flag_key=<key>&depth=<n>` — wraps the
  existing `DependencyGraphBuilder.get_impact_fast()` (Redis-backed, `services/intelligence/app/graph/builder.py`)
  to return a subgraph (nodes + weighted edges) centered on `flag_key`, traversing to
  `depth` hops. Falls back to the existing `get_impact()` DB-scan path on Redis cold-start,
  matching the current fallback contract.
- New endpoint `GET /api/v1/graph/critical-flags` — computes a "Dependency Health Score" per
  flag from existing graph data: `score = (in_degree + out_degree) * avg_edge_weight *
  blast_radius_multiplier`, where `blast_radius_multiplier` is `4/3/2/1` for
  `BLOCKED/HIGH/MEDIUM/LOW` (reusing, not reinventing, the evaluator's already-computed
  blast-radius tier). Returns top-N most critical flags, sorted descending. This starting
  formula may be tuned during implementation if it doesn't rank sensibly against real data,
  but the shape (degree × coupling strength × blast-radius weight) is fixed by this spec.
- No new tables/migrations — reads existing Redis sorted sets
  (`tombstone:depgraph:{flag_key}`) and existing `audit_log`/blast-radius data. Purely
  additive, read-only surface.
- New MCP tool `tombstone_get_dependency_graph` in `workspace-mcp/src/tools/flags.ts`,
  following the existing pattern of the current 8 tools.

### Frontend (`workspace-dashboard/`)
- New "Dependencies" tab on the flag detail page.
- Force-directed graph rendering built against the existing `d3` dependency (already in
  `workspace-dashboard/package.json`) — no new graph-library dependency.
- Click-node interaction: highlight the connected subgraph, show edge weights (co-change
  strength) on hover.
- "Disable simulation" mode: client-side graph traversal from the clicked node, greys
  out/highlights the affected downstream set, shows an affected-flag count.
- Critical-flags panel: sorted list backed by `/critical-flags`, linking each entry to its
  detail page.

### Testing
- Python unit tests for the two new endpoints, mirroring existing `services/intelligence/tests/`
  patterns.
- Vitest suite for the new dashboard tab's rendering/interaction logic, per repo convention.

## 7. Phasing & Version

Lands as **v1.5.0** — a single minor release covering both tracks (neither track alone is
disruptive enough to warrant its own version; both are backlog-closing work, not
experimental). Each phase is an independently mergeable PR (or PR set) to `develop`, per the
existing branch strategy (`BRANCHES.md`).

| Phase | Work | Depends on |
|---|---|---|
| 1 | Canonical spec doc (`docs/SDK_CONTRACT.md` rewrite) + expanded `test-contract/vectors.json` | — |
| 2 | Java SDK parity + P0 cleanup + naming | Phase 1 |
| 3 | Ruby SDK parity + P0 fix + naming | Phase 1 (implemented after Phase 2, carrying lessons forward) |
| 4 | .NET SDK parity + P0 fix + naming | Phase 1 (implemented after Phase 3) |
| 5 | Dependency Visualization backend (intelligence endpoints + MCP tool) | — (independent of 1–4) |
| 6 | Dependency Visualization frontend (dashboard tab) | Phase 5 |
| 7 | Release: CHANGELOG entries, version bump, tag v1.5.0, GitHub release | Phases 2–4 and 5–6 merged |

Phases 2–4 (Track A) and 5–6 (Track B) are mutually independent and can run in parallel as
two workstreams; within Track A, Java → Ruby → .NET stay strictly sequential.

## 8. Testing & Verification Strategy

- Each SDK PR must pass its own existing unit tests (unchanged behavior for steps 1/5) plus
  the new vector-harness suite (100% of applicable vectors — hash vectors apply to all,
  prerequisite/rule/operator vectors apply once each SDK implements the corresponding step).
- `docs/SDK_CONTRACT.md`'s rewritten parity matrix must be re-verified against actual source
  after each SDK PR merges (same read-the-actual-code discipline used during this design's
  research phase — do not trust the previous PR's self-report).
- Dependency Visualization: new endpoints get integration tests against a seeded Redis
  dep-graph fixture; dashboard tab gets Vitest coverage for graph render + simulation logic;
  manual verification via `make dev` + browser check of the new tab before considering Phase
  6 done (per this project's UI-verification convention).
- No live-cluster or GitOps verification needed — this release touches no GitOps/K8s paths.

## 9. Risks & Known Limitations After This Release

- TS and Python SDKs remain mutually divergent (case-sensitivity, prerequisite semantics,
  rule structure) — explicitly deferred, not a regression introduced by this release.
- Regex targeting-rule operator remains unimplemented across all 5 SDKs.
- `.NET` SDK's directory name (`flagmind-dotnet`) may remain inconsistent with its
  project/namespace naming if a full directory rename is deferred — decision to be made
  during Phase 4 implementation.
- No load/scale testing of the new dependency-graph endpoints at "5,000+ flags" scale is in
  scope for this release; existing Redis-backed `get_impact_fast()` big-O characteristics are
  inherited as-is.
